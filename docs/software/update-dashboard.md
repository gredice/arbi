# Device release and update dashboard

The authenticated Releases screen implements [#75](https://github.com/gredice/arbi/issues/75) under [ADR-0021](../decisions/0021-isolated-update-dashboard.md). Its [client](../../apps/arbi-dashboard/src/dashboard/updates.tsx) uses the existing protected update API; [operation authority and limits](update-operations.md) remain on the edge.

Use **Read update inventory** to retrieve signed compatibility, accepted managed capabilities, reported slots and bounded durable history. Use **Read published artifacts** independently to read the immutable publisher catalog. Neither read starts a download or install. Select a release and an ordered prefix; the edge coordinator is last. Size, current allowance, coverage, metered status and expected policy outcome appear before the request. Retry bytes can exceed artifact size. Any explicit override uses current update and engineering permissions and preserves its original audit identity.

**Request update** journals intent without changing installed health. **Advance or recover existing operation** performs one bounded step after current authority and local checks. **Refresh operation status** reads only. Results distinguish desired, installed and confirmed release, staging/transfer phase, actual application-payload charges, receipt gaps and unresolved conservative bounds. Wire/carrier quantities are unknown. Rollback requires observed healthy target recovery; a failed canary halts the remaining group.

A URL request key recovers an acknowledged operation after a lost response; the operation ID attaches after reload. Protected data stays in memory and clears on hidden/offline/expired lifecycle boundaries. The original actor owns mutations. Engineering display alone grants no update permission. Local preflight reasons remain visible, and no UI control substitutes for independent retention, line clearance, power or interlock evidence.

The web deployment identity is a separate compile-time build record: Git SHA, dirty-tree flag, build time and environment. It never comes from a firmware manifest. The isolated fixture's manifests are signed synthetic artifacts; the screen does not claim that these establish a live reviewed publisher's acceptance.

Run `pnpm --filter @arbi/dashboard test:browser` after building both dashboard and edge and installing the pinned Chromium. The harness creates its own socket-only native PostgreSQL cluster, private profiles, loopback worker and synthetic SQLite slots, then removes them. The [proxy](../../apps/arbi-dashboard/src/updates/proxy.ts) is available only in an explicitly provisioned local test composition; normal/preview HTTP startup fails closed. Private credentials and fault controls are never rendered or committed. [Evidence](../evidence/update-dashboard.md) separates browser/software results from live and physical acceptance.
