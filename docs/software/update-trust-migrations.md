# Signing trust and rollback-compatible data

Work record: [#74](https://github.com/gredice/arbi/issues/74), [ADR-0019](../decisions/0019-isolated-trust-and-migration-recovery.md), [software evidence](../evidence/update-trust-migrations.md).

`UpdateTrustStore` requires a private file/directory, test realm, site/device binding, pinned public root, provisioning-review reference and trusted reliable UTC clock. It never accepts a private root key. Root policies are closed signed records with overlapping release-key windows, explicit revoked tombstones and monotonic security floors. Store acknowledgement uses SQLite FULL synchronization; clock checkpoints survive restart. Unknown/untrusted, revoked, out-of-window or below-floor artifacts are rejected before any migration admission.

Offline root owners approve policy/key additions and recovery checkpoints. A protected release publisher signs immutable manifests/artifacts with its release key and obtains root approval for release security-version bindings. Devices receive public trust only. Ordinary dashboard update requests cannot replace roots or touch OTP/fuses. Production key custody, publication and physical root provisioning need their own reviewed deployment/recovery procedure; the source adapter is restricted to synthetic test realms.

A planned overlap policy authorizes old/new release keys together. A later policy retains the old key as revoked and can raise a security floor. An offline device with expired policy refuses artifacts, obtains a currently valid root-signed checkpoint through reviewed private recovery, checks the revision/floor/tombstones, and records the recovery reference. A missing predecessor without that reference remains blocked. Replacing the root requires a separate reviewed reprovisioning procedure and an independently verified recovery image/physical protection plan; there is no normal-update root replacement API.

`plan` evaluates the declared release set, every mixed intermediate state and every rollback prefix, with current manifest signature/key/floor checks. It is a compatibility report, not authority or proof of actually installed versions. The fixture's edge bridge accepts the older peer versions before peers advance. Reversing the order creates an incompatible state. Raising the security floor blocks return to the old security version; a separately signed compatible replacement at security version 2 preserves usable recovery without lowering the floor. Failed-trial fallback and explicit downgrade both require an eligible baseline; a confirmed policy floor cannot be waived by calling a rollback method.

`UpdateMigrationStore` persists representative voltage/speed/revision data, immutable prior snapshots and a prepared marker before applying a named transform. A restart after preparation exposes `resume-or-restore-prior-data`; prior data remains intact. The isolated `synthetic-reversible-migration` halves a bounded speed limit and advances data version 1.0.0 to 1.1.0. Unknown transforms require review and keep the prior snapshot. Current trust is checked again before apply/rollback, and reverse-data compatibility must match the baseline manifest. These records never authorize motion or establish an installed firmware boot.

Capacity exhaustion, clock uncertainty and corruption fail closed. Diagnostic responses contain fixed recovery reasons and no provider exception text, keys or signing material. This local operational journal is separate from canonical human update admission/audit; [#73](https://github.com/gredice/arbi/issues/73) owns that composition and observed target outcomes. Existing signed update contracts and local protection continue to control installation; no field installation is added here.
