# ARBI dashboard and HTTP boundary

This Next.js app implements the [authenticated dashboard shell](../../docs/software/dashboard-shell.md) for [#39](https://github.com/gredice/arbi/issues/39), simulation-only [device enrollment and inventory boundary](../../docs/software/device-enrollment.md) for [#21](https://github.com/gredice/arbi/issues/21), and [image metadata/private storage boundary](../../docs/software/image-storage.md) for [#22](https://github.com/gredice/arbi/issues/22). It contains working HTTP handlers, protected PostgreSQL migrations, identity/proof verification, a Vercel private Blob SDK adapter and lifecycle tests. The [durable command job and exclusive manual lease boundary](../../docs/software/command-jobs.md) implements #28. [Outbound realtime and authoritative recovery](../../docs/software/realtime-recovery.md) implements the source/host slice of #29. Detailed diagnostics, live provider provisioning, live media and physical device adapters remain separate work.

The shell serves site-scoped user/engineering pages and protected `/api/sites/:siteId/dashboard/:view` reads. [Setup, contract, isolated provider and browser commands](../../docs/software/dashboard-shell.md) describe the boundary; [source/hosted evidence](../../docs/evidence/dashboard-shell.md) keeps test deployment separate from production. Ordinary starts remain unconfigured. The explicit isolated test provider uses current PostgreSQL sessions/memberships and the committed bounded plant model; it never grants commands or live-device authority.

The mounted route is `/api/sites/:siteId/enrollment/:action`. An unconfigured build returns a redacted `503`; it never installs a fixture identity provider or an in-memory registry by default. Trusted server composition uses [createEnrollmentServer](src/enrollment/server.ts) with the accepted Gredice identity/current directory/resource resolver, approved browser origins and a migrated database, then [configureEnrollment](src/enrollment/runtime.ts). The resource resolver and directory are current server-side adapters, never body-supplied roles or site claims. This initial slice rejects production and hardware scope.

Media routes are `/api/sites/:siteId/media/:action` and `/api/sites/:siteId/images/:imageId/:action`; they also fail closed until explicitly installed via [createMediaServer](src/media/server.ts)/[configureMedia](src/media/runtime.ts). The service provides strict upload metadata, retry-safe direct PUT grants, idempotent verified completion, original/thumbnail access, revocation records and repeatable deletion/cleanup. [Media documentation](../../docs/software/image-storage.md) specifies exact JSON bodies, trusted capture provenance, signed URL expiry/revocation limits, stored-payload accounting, operational cleanup/retention requirements and remaining live gates. Apply [0002-media.sql](migrations/0002-media.sql) explicitly with `pnpm --filter @arbi/dashboard db:migrate:media` and privately supplied `ARBI_MEDIA_DATABASE_URL`; `0001` and its command are unchanged. Provision authoritative media-site bindings separately; never derive ownership from request claims or enable fixture fallbacks.

[postgresDatabase](src/enrollment/store.ts) uses a server-side `pg.Pool` for the selected Neon PostgreSQL boundary. Configure pooled connections with a bounded connection timeout; no provider URL or credential is supplied in this repository. Run the [migration](migrations/0001-enrollment.sql) explicitly via `pnpm --filter @arbi/dashboard db:migrate` with `ARBI_ENROLLMENT_DATABASE_URL` supplied privately. No migration or commissioning happens during build/start. Provision the initial simulated inventory through the protected `simulationRegistry`/`PostgresRegistryStore.provision` server interface using validated configuration and the account from the authoritative site catalog. Existing rows cannot be overwritten by bootstrap.

```sh
pnpm install --frozen-lockfile
pnpm --filter @arbi/protocol build
pnpm --filter @arbi/gredice build
pnpm --filter @arbi/dashboard lint
pnpm --filter @arbi/dashboard typecheck
pnpm --filter @arbi/dashboard test
pnpm --filter @arbi/dashboard test:postgres
pnpm --filter @arbi/dashboard build
pnpm --filter @arbi/dashboard test:http
```

The ordinary suite uses embedded PostgreSQL (PGlite), temporary synthetic configuration, ephemeral device keys and a loopback HTTP Blob fixture that exercises the real SDK without cloud credentials. The separate `test:postgres` requires `pg_config`, `initdb`, `pg_ctl` and local socket/loopback access. It creates/removes its own temporary PostgreSQL cluster, disables TCP listening, and tests independent connections, migration preservation and transaction rollback for enrollment and media. After build, `test:http` starts/stops its own loopback Next.js server and verifies unprovisioned enrollment/media responses stay redacted and fail closed. CI invokes all three. The ordinary suite marks host-specific tests skipped unless the dedicated launcher supplies its isolated socket; this is not a substitute for running `test:postgres`.

Ordinary fixture files run sequentially to avoid competing database startup starving bounded loopback requests. This finite test process also disables **WebAssembly code** garbage collection with `--no-wasm-code-gc`: Node 24.15.0 Linux CI aborted in V8's `UnregisterWasmAllocation` with `jit_page_->allocations_.erase(addr) == 1`. The signature matches [Node issue #66366](https://github.com/nodejs/node/issues/66366) and the [upstream V8 wrapper lifetime fix](https://github.com/v8/v8/commit/9b8ca54d5a). This is a test-only workaround that retains compiled Wasm code until process exit; JavaScript garbage collection, assertions and request deadlines remain unchanged. Remove the flag after the pinned Node release includes the fix and repeated Linux fixture runs pass without it. Application `dev`/`start`/`build` and the native PostgreSQL/HTTP launchers do not use this flag; PGlite is a development dependency.

`pnpm --filter @arbi/dashboard start` serves a built, fail-closed app. Source tests and local database checks do not establish live Gredice/Neon provisioning, Vercel team deployment, power-loss durability, installed commissioning, safe actuation or physical acceptance. Those gates remain unverified.

## Durable audit foundation

The [audit adapter](src/audit/server.ts) adds signed device ingestion at `/api/sites/:siteId/audit/ingest`, transactional cloud intent/authorization/outbox admission and protected append-only history. It requires explicit server composition with current enrollment and an independently trusted event-ID evidence resolver; missing configuration returns 503. Device ingestion remains simulation-only under current enrollment. Apply additive `0003-audit.sql` after unchanged 0001/0002 with `pnpm --filter @arbi/dashboard db:migrate:audit` and operator-only migration credentials. Never use migration ownership as the application role.

[Audit durability](../../docs/software/audit-durability.md) owns roles, replay/clock/gap semantics, checkpoint/backup threat limits and host evidence. Shared [SQLite local APIs](../../packages/arbi-audit/README.md) remain independent of edge job orchestration. `test:postgres` preserves independent enrollment/media suites and runs native audit tests in a separate database within its fresh socket-only cluster. This does not deploy provider resources, enable recording or clear physical safety gates.

## Durable command jobs and manual sessions

Mounted `/api/sites/:siteId/jobs/:action` handlers implement persisted intent/status, exclusive fenced human leases, signed receiver snapshots, bounded device polling and immutable protocol outcome receipts. [createJobsServer](src/jobs/server.ts)/[configureJobs](src/jobs/runtime.ts) require explicit trusted current identity/resource/session authorization and migrated storage. Missing configuration denies every action. Apply additive [0004-jobs.sql](migrations/0004-jobs.sql) after unchanged 0001/0002/0003 via `db:migrate:jobs` with privately supplied `ARBI_JOBS_DATABASE_URL`. Admission uses the existing transactional audit/outbox hook.

[Command job documentation](../../docs/software/command-jobs.md) specifies exact bodies, resolver requirements, restart/clock/fence semantics, cancellation versus independent stop receipts, status provenance and remaining gates. Native `test:postgres` runs its independent-connection/crash/replay/rollback proof; built `test:http` checks all mounted job/lease actions fail closed. This is a simulation-only cloud boundary, with no broker, local job orchestration, provider provisioning or physical enablement.

## Outbound realtime recovery

Mounted `/api/sites/:siteId/realtime/:action` supports human attach/recover and signed current-device attach/recover. Explicit [server composition](src/realtime/server.ts)/[runtime installation](src/realtime/runtime.ts), current authorization, migrated storage and private Ably SDK adapter are required. Apply additive [0005-realtime.sql](migrations/0005-realtime.sql) after 0001–0004 with `db:migrate:realtime`; configure bounded operator `realtime:maintain` scheduling separately. [Semantics, roles, limits and exact external gates](../../docs/software/realtime-recovery.md) and [host evidence](../../docs/evidence/realtime-recovery.md) distinguish source/SDK fixtures/native PostgreSQL from actual Ably/Neon/Vercel/mobile acceptance. Build the edge consumer before running native `test:postgres`; root `pnpm test --concurrency=1` and CI already build it. No fixture server or identity is a deployment default.

The opt-in [browser consumer](src/realtime/browser-consumer.ts), [HTTPS adapter](src/realtime/browser-http.ts) and [Ably browser subscription](src/realtime/browser-ably.ts) use the same authoritative API. Trusted composition supplies the current ARBI bearer; page teardown aborts recovery and clears state. Hints coalesce, replay gaps reset, broker downtime permits bounded HTTPS recovery, and request/admission/application-byte budgets apply. The shell does not start this client by default. `pnpm --filter @arbi/dashboard test:browser` includes actual Chromium/SDK/native PostgreSQL recovery and revocation checks alongside the shell tests; install the pinned Chromium with `pnpm --filter @arbi/dashboard exec playwright install chromium` first.


## Current telemetry and bounded history

The [telemetry adapter](src/telemetry/server.ts) mounts signed device ingestion and protected current/history/configured-assembly inventory queries at `/api/sites/:siteId/telemetry/:action`. It retains boot/sequence/configuration and sample provenance, visible gaps/resets, explicit unavailable/stale values, quality-separated minute/hour aggregates, full event/fault detail and small private trace attachments. Current state and replay/outbox hints commit together. Trusted server composition is explicit and simulation-only; an ordinary start returns unavailable.

Apply additive [0006-telemetry.sql](migrations/0006-telemetry.sql) after migrations 0001–0005 using `pnpm --filter @arbi/dashboard db:migrate:telemetry`. [Telemetry history](../../docs/software/telemetry-history.md) specifies API fields, retention/row/byte/request/query budgets, role grants and `telemetry:maintain` for idle sites. The ordinary and native PostgreSQL suites include the committed [telemetry evidence](../../docs/evidence/telemetry-history.md); `test:http` checks the mounted fail-closed routes. Provider provisioning and physical acceptance remain separate.

## Usage ingestion and rollups

The [usage adapter](src/usage/server.ts) mounts `/api/sites/:siteId/usage/:action` for signed bounded source-window admission, current-authority history/period reads and audited append-only corrections. It requires explicit trusted [runtime installation](src/usage/runtime.ts) and fails closed by default and in branch previews. Apply [0007-usage.sql](migrations/0007-usage.sql) after 0001–0004 with `pnpm --filter @arbi/dashboard db:migrate:usage`; keep migration ownership separate from application privileges. [Usage documentation](../../docs/software/usage-rollups.md) specifies exact request bodies, replay/overlap semantics, layer separation, UTC days, plan-timezone periods, estimated boundary allocation, rollover and hard bounds. [Host evidence](../../docs/evidence/usage-rollups.md) separates embedded SQL from native audit/concurrency checks and actual cellular/provider acceptance.
